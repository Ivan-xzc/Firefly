进入进程这一版块之前，我们先区分两组概念：

并发与并行

并发：宏观上同时运行，微观上交替执行，单核 CPU 上，操作系统利用时间片轮转，多个进程快速切换

并行：同一时刻，多个任务真正同时执行，需要多个 CPU 核心

进程与程序

进程：程序的一次执行过程，是操作系统进行资源分配的基本单位

程序：静态的、存放在磁盘上的指令与数据集合，是文件

一个程序可以对应多个进程

# 进程控制

进程控制的主要任务是创建和撤消进程以及实现进程的状态转换
由**内核**来实现。

结构特征：程序段，数据段，**进程控制块PCB**

进程控制的实现：原语

必须在**内核态**下执行，且常驻内存

## fork()创建进程
```
fork() 会复制当前进程，创建一个几乎一样的新进程。原来的进程叫父进程，新创建的进程叫子进程。
这两个进程都会从 fork() 之后的代码继续执行。
同一句 fork()，在父进程和子进程中返回值不同：

返回值	所在进程	含义
pid > 0	父进程	返回子进程的 PID
pid == 0	子进程	表示当前是子进程
pid < 0	父进程	创建失败

父进程和子进程有很多相似之处：
代码段相同
数据内容初始相同

但是它们是两个不同的进程，彼此相互独立：
PID 不同
PCB 不同
进程状态不同
调度顺序不确定
地址空间相互独立
```

# 线程

进程包含了两个概念：资源拥有者和可执行单元

现代操作系统将资源拥有者称为进程（process），可执行单元称为线程（thread）

线程额外的资源：运行状态、保存上下文（程序计数器PC）、执行栈、资源共享机制

引入线程好处

• 减少并发程序执行时所付出的时空开销，使得并发粒度更细、并发性更好
  线程比进程轻量：容易创建、撤销

• 有些应用要求并行实体共享同一个地址空间和所有可用数据的能力

注：

1.一个进程可以拥有多个线程，而一个线程同时只能被一个进程所拥有。

2.**进程是资源分配的基本单位，线程是处理机调度的基本单位**，所有的线程共享其所属进程的所有资源与代码。

3.线程执行过程之中很容易进行协作同步，而进程需要通过消息通信进行同步。

4.线程共享进程的数据的同时，有自己私有的的堆，栈，寄存器组。

# 用户级线程和内核级线程

用户级线程和内核级线程的区别，关键在于：

线程的创建、调度和管理，是由用户态线程库完成，还是由操作系统内核完成。

用户级线程指的是：

线程由用户态的线程库管理，操作系统内核并不知道这些线程的存在。
操作系统看到的仍然只是一个进程。

缺点：易阻塞

内核级线程指的是：

线程由操作系统内核直接管理，内核知道每一个线程的存在。

缺点：开销大

| 比较项               | 用户级线程                       | 内核级线程                       |
| -------------------- | -------------------------------- | -------------------------------- |
| 管理者               | 用户态线程库                     | 操作系统内核                     |
| 内核是否知道线程存在 | 不知道                           | 知道                             |
| 线程切换开销         | 小                               | 较大                             |
| 阻塞系统调用影响     | 一个线程阻塞可能导致整个进程阻塞 | 一个线程阻塞不影响同进程其他线程 |
| 是否能利用多核并行   | 一般不能充分利用                 | 可以                             |
| 调度单位             | 内核调度进程，用户库调度线程     | 内核直接调度线程                 |
| 灵活性               | 高                               | 较低                             |
| 系统调用开销         | 小                               | 较大                             |

# 常见线程模型
1. 多对一模型

多个用户级线程对应一个内核调度实体。

用户线程 T1 T2 T3
        ↓
一个内核线程

优点：切换快。
缺点：一个线程阻塞，可能整个进程阻塞；难以利用多核。

2. 一对一模型

一个用户线程对应一个内核线程。

用户线程 T1 → 内核线程 K1
用户线程 T2 → 内核线程 K2
用户线程 T3 → 内核线程 K3

优点：能利用多核，一个线程阻塞不影响其他线程。
缺点：创建和切换开销较大。

Java 中的线程在现代主流操作系统上通常就是这种模型

3. 多对多模型

多个用户级线程映射到多个内核级线程。

用户线程 T1 T2 T3 T4 T5
        ↓
内核线程 K1 K2 K3

优点：兼顾用户级线程的灵活性和内核级线程的并行能力。
缺点：实现复杂。

# 线程安全与可重入

线程安全强调：

多个线程同时调用同一段代码时，结果仍然正确。

可重入强调：

一个函数执行到一半时，又被再次调用，仍然能正确执行。

• 可重入不一定线程安全

• 线程安全不一定可重入

二者无必然联系

# 同步与互斥（重）

**互斥**强调的是：

多个进程不能同时使用某个共享资源，必须一个一个来

互斥的核心要求：

对于同一个临界资源，同一时刻最多只能有一个进程进入临界区

**同步**强调的是：

多个进程之间存在执行先后关系，需要按照一定顺序推进。

同步的核心要求：

某些进程必须等待其他进程到达某个状态后才能继续执行

# 互斥与同步算法

## 互斥区管理原则

```
• 空闲让进：临界资源处于空闲状态，允许进程进入临界区。如，临界区内仅有一个进程执行
• 忙则等待：临界区有正在执行的进程，所有其他进程则不可以进入临界区
• 有限等待：对要求访问临界区的进程，应在保证在有限时间内进入自己的临界区，避免死等。
• 让权等待：当进程（长时间）不能进入自己的临界区时，应立即释放处理机，尽量避免忙等。
```

## 软件方法

Dekker 算法通过 flag 表示进程是否想进入临界区，通过 turn 决定竞争时谁优先，从而实现两个进程之间的互斥、空闲让进和有限等待。

Peterson 算法代码
```c
do {
    flag[i] = true;      // 表示 Pi 想进入临界区
    turn = j;            // 把优先权让给对方 Pj

    while (flag[j] && turn == j) {
        // busy waiting，忙等待
    }

    // 临界区
    critical_section();

    flag[i] = false;     // Pi 离开临界区

    // 剩余区
    remainder_section();

} while (true);
```
Peterson 算法的思想可以概括为：

我先声明我想进临界区，但如果你也想进，我把优先权让给你

Dekker 是“看 turn 决定谁让步”，Peterson 是“我想进，但我先让你”。

Peterson 算法主要解决 两个进程互斥,

而 Lamport 面包店算法可以解决 多个进程互斥

它的核心思想是：

谁先取到更小的号，谁先进入临界区；号码相同，就按进程编号排序。

## 信号量机制(PV)（重）

信号量只能通过初始化和两个标准的原语来访问，作为OS核心代码执行，不受进程调度的打断

```c
P(S) {
    S--;
    if (S < 0) {
        阻塞当前进程;
    }
}

V(S) {
    S++;
    if (S <= 0) {
        唤醒一个等待该信号量的进程;
    }
}
```

P 操作：申请资源

P(S) 的含义是：

申请一个资源，如果资源不足，就阻塞等待。

V 操作：释放资源

V(S) 的含义是：

释放一个资源，如果有进程正在等待，就唤醒一个。

P，V均为原子操作

• S.value为正时表示资源的个数

• S.value为负时表示等待进程的个数

• 互斥

– 利用信号量实现进程互斥（S=1）

这就是互斥信号量，也常叫 mutex。

• 同步

– 利用信号量实现进程同步（S=0）

| 用途 |   信号量初值 | 含义              | 典型结构                |
| 互斥 | `S = 1` | 一开始临界资源可用       | `P(S)` 进入，`V(S)` 退出 |
| 同步 | `S = 0` | 一开始条件不满足，需要等待通知 | 前者 `V(S)`，后者 `P(S)` |

## “信号量集”机制

信号量集机制可以理解为：

把多个信号量组合起来，一次性申请或释放多个资源，用来解决“一个进程需要同时获得多类资源”的同步问题。

否则单独信号量可能造成死锁

信号量集机制的一个重要形式是 AND 型信号量。

它的思想是：

一个进程需要多个资源时，必须同时申请成功，才能继续执行。

## 管程机制(Monitor)

管程是一种高级同步原语。

把共享数据、访问共享数据的操作，以及同步控制机制封装在一起的一种结构。

进程不能直接访问管程里的共享数据，只能通过管程提供的过程访问。类似于面向对象

管程有一个核心规则：

任意时刻，最多只有一个进程在管程内部执行

即自动互斥

条件变量c：解决同步问题

每个条件变量表示一种等待原因，并不取具体数
值－－相当于每个原因对应一个队列。

wait(c) 表示：

当前进程因为条件不满足而等待，并且释放管程的互斥权。

signal(c) 表示：

唤醒一个正在条件变量 c 上等待的进程。

如：
```c
procedure get() {
    while (count == 0) {
        wait(notEmpty);
    }

    item x = remove();
    count--;

    signal(notFull);

    return x;
}
```

信号量的 P/V：作用于资源数量
管程的 wait/signal：作用于条件变量

重点：

管程中的 wait 会释放管程互斥权，访问条件变量必须拥有管程的锁

```
Hoare 管程

signal(c) 后，被唤醒的进程立即执行，发出 signal 的进程让出管程。

紧急等待队列的优先级大于入口等待队列

Mesa 管程

signal(c) 后，被唤醒的进程只是进入就绪队列，之后再竞争管程。

signal 后：等待进程不一定马上运行
```

## 进程通信

## 管道 Pipe

管道是一种最基本的进程间通信方式。

管道通常是半双工的，也就是数据一般只能单向流动

普通管道一般用于具有亲缘关系的进程，比如父子进程。

命名管道 FIFO

普通管道通常只能用于父子进程，而命名管道可以用于没有亲缘关系的进程

消息传递——两个通信原语（OS系统调用）

## 共享内存 Shared Memory

共享内存是最快的进程间通信方式之一。

它的思想是：

操作系统把同一块物理内存映射到多个进程的地址空间中，使这些进程都能访问这块内存。

当多个进程共享同一块内存区域，由于共享内存可以同时读但不能同时写，则需要同步机制约束（互斥锁,条件变量和信号量都可以）。

一、生产者—消费者问题
```
1. 问题描述

有一个大小为 N 的缓冲区。

生产者往缓冲区放产品，消费者从缓冲区取产品。

2. 信号量设置
semaphore mutex = 1;  // 互斥访问缓冲区
semaphore empty = N;  // 空缓冲区数量
semaphore full = 0;   // 已有产品数量，控制同步

3. 生产者
Consumer() {
    while (true) {
        P(full);          // 申请一个已有产品
        P(mutex);         // 进入临界区

        get_item();       // 从缓冲区取出产品

        V(mutex);         // 离开临界区
        V(empty);         // 空缓冲区数量 +1

        consume_item();   // 消费产品
    }
}

4. 消费者
Consumer() {
    while (true) {
        P(full);          // 申请一个已有产品
        P(mutex);         // 进入临界区

        get_item();       // 从缓冲区取出产品

        V(mutex);         // 离开临界区
        V(empty);         // 空缓冲区数量 +1

        consume_item();   // 消费产品
    }
}
```
二、读者—写者问题（读者优先）
```
1. 问题描述

多个进程共享一个文件或数据区。

要求：

1. 多个读者可以同时读
2. 写者写的时候，不能有其他读者或写者
3. 读和写互斥
4. 写和写互斥
2.信号量设置
semaphore rw = 1;     // 控制对共享文件的访问
semaphore mutex = 1;  // 保护 readcount
int readcount = 0;
3.读者
reader() {
    while (true) {
        P(mutex);
        readcount++;
        if (readcount == 1) {
            P(rw);
        }
        V(mutex);

        读文件;

        P(mutex);
        readcount--;
        if (readcount == 0) {
            V(rw);
        }
        V(mutex);
    }
}
第一个读者负责锁住文件，不让写者写；
后续读者可以一起读；
最后一个读者负责释放文件，让写者可以写。
4.写者
writer() {
    while (true) {
        P(rw);

        写文件;

        V(rw);
    }
}
```
# 进程调度

## 调度分类

高级调度：又称为“宏观调度”、“作业调度”。

从用户工作流程的角度，一次提交的若干个作业，对每个作业进行调度。时间上通常是分钟、小时或天。

内外存交换：又称为“中级调度”

从存储器资源的角度，将进程的部分或全部换出到外存上，将当前所需部分换入到内存。

低级调度：又称为“微观调度”、“进程或线程调度”。

从CPU资源的角度，执行的单位，时间上通常是毫秒。因为执行频繁，要求在实现时达到高效率。


## 进程切换

进程（上下文）切换的步骤:

```
– 保存处理器的上下文，包括程序计数器和其它寄存器
– 用新状态和其它相关信息更新正在运行进程的PCB
– 把进程移至合适的队列：就绪、阻塞
– 选择另一个要执行的进程
– 更新被选中进程的PCB（新状态等）
– 从被选中进程中重装入CPU 上下文
```

批处理系统:

周转时间：作业从提交到完成（得到结果）所经历的时间

吞吐量：单位时间内所完成的作业数，跟作业本身特性和调度算法都有关系

平均周转时间不是吞吐量的倒数，因为并发执行的作业在时间上可以重叠。

分时系统:

响应时间：用户输入一个请求（如击键）到系统给出首次响应（如屏幕显示）的时间

实时系统:

截止时间：开始截止（最早开始）时间和完成截止（最晚完成）时间

## 占用CPU的方式

不可抢占方式

一旦处理器分配给一个进程，它就一直占用处理器，直到该进程自己因调用原语操作或等待I/O等原因而进入阻塞状态，或时间片用完时才让出处理器，重新进行

可抢占方式

就绪队列中一旦有优先级高于当前运行进程优先级的进程存在时，便立即进行进程调度，把处理器转给优先级高的进程

## 进程的分类

CPU密集型进程和IO密集型进程

批处理进程

无需与用户交互，通常在后台运行

编译器、科学计算

交互式进程

与用户交互频繁，因此要花很多时间等待用户输入

Word、触控型GUI

实时进程

有实时要求，不能被低优先级进程阻塞

响应时间要短且要稳定

视频/音频、控制类


## 时间片

一个时间段，分配给调度上CPU的进程，确定了允许该进程运行的时间长度

优先级倒置现象：高优先级进程（或线程）被低优先级进程（或线程）延迟或阻塞。

解决方法：
让低优先级进程尽快释放资源

1.优先级置顶（Priority Ceiling）

将阻塞或延迟高优先级进程的低优先级进程优先级提到最高，让其尽快完成释放资源

2.优先级继承（Priority Inheritance）

# 死锁

死锁发生原因

– 资源竞争

– 并发执行的顺序不当

• 可剥夺资源：是指某进程在获得这类资源后，该资源可以再被其他进程或系统剥夺。如CPU，内存；

• 非可剥夺资源：当系统把这类资源分配给某进程后，再不能强行收回，只能在进程用完后自行释放。如磁带机、打印机；

• 临时性资源：这是指由一个进程产生，被另一个进程使用，短时间后便无用的资源，故也称为消耗性资源。如消息、中断；


![](images/image-43.png)

活锁（livelock）：是指任务或者执行者没有被阻塞，由于某些条件没有满足，导致一直重复尝试，失败，尝试，失败。

饥饿(starvation)：某些进程可能由于资源分配策略的不公平导致长时间等待。


## 处理死锁的基本办法

– 死锁预防（Deadlock Prevention）

– 死锁避免（Deadlock Avoidance）

– 死锁检测（Deadlock Detection）

死锁预防是排除死锁的静态策略,它使产生死锁的四个必要条件不能同时具备，从而对进程申请资源的活动加以限制，以保证死锁不会发生。

死锁避免是排除死锁的动态策略,即分配资源时判断是否会出现死锁，有则加以避免

系统进入不安全状态（四个死锁的必要条件同时发生）也未必会产生死锁。当然，产生死锁后，系统一定处于不安全状态。


## 银行家算法（重）

银行家算法是死锁避免方法：系统在每次分配资源前，先判断“分配后会不会进入不安全状态”。如果不安全，就暂时不分配。
```
假设有 n 个进程，m 类资源。

Available
当前系统还剩多少资源。
Available[j] = 第 j 类资源当前可用数量

Max
每个进程最多需要多少资源。
Max[i][j] = 进程 Pi 对第 j 类资源的最大需求

Allocation
当前已经分给每个进程多少资源。
Allocation[i][j] = Pi 当前已占有第 j 类资源数量

Need
每个进程还需要多少资源。
Need[i][j] = Max[i][j] - Allocation[i][j]

安全性算法

判断当前状态是否安全。

步骤：

1.设置：
Work = Available
Finish[i] = false
2.找一个满足条件的进程 Pi：
Finish[i] == false
且 Need[i] <= Work

意思是：当前剩余资源能满足 Pi 的剩余需求。

3.假设 Pi 执行完成，释放资源：
Work = Work + Allocation[i]
Finish[i] = true
4.重复寻找。
5.如果最后所有 Finish[i] == true，则系统安全；否则不安全。

资源请求算法

当进程 Pi 请求资源 Request[i] 时：

第一步：检查是否超过最大需求
Request[i] <= Need[i]

否则说明进程申请超过了自己声明的最大需求，非法。

第二步：检查系统当前是否够分
Request[i] <= Available

否则 Pi 必须等待。

第三步：试探性分配
Available = Available - Request[i]
Allocation[i] = Allocation[i] + Request[i]
Need[i] = Need[i] - Request[i]
第四步：执行安全性检查

如果分配后系统仍安全，则正式分配。

如果不安全，则撤销分配，让 Pi 等待。

它要求系统提前知道：

每个进程的最大资源需求 Max

这是它在实际系统中不常用的重要原因。
```

## 死锁解除

两种方法：资源剥夺法、撤销进程法

–撤消进程：使全部死锁的进程夭折掉；按照某种顺序逐个地撤消（回退）进程，直至有足够的资源可用，死锁状态消除为止，

–剥夺资源：使用挂起/激活挂起一些进程，剥夺它们的资源以解除死锁，待条件满足时，再激活进程。
